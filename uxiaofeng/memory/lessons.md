## 2026-11-01 · 🔴 重大数据损坏：78 个记忆文件被 Git 冲突标记污染

- **现象**: `memory/` 下 78 个文件 + `uxiaofeng/memory/` 79 个文件正文夹带 `<<<<<<< HEAD` / `=======` / `>>>>>>>` 冲突标记，最长持续 4 天无人发现
- **根因**: merge commit `4dbaea3`（2026-10-28「解决 reflexion_journal.md add/add 冲突」）在解决一个文件的冲突时，把**其余 78 个文件的冲突标记原样提交**了。两个父提交（33d473e / f84ca06）的对应文件都是干净的 → 纯粹的解决冲突操作失误
- **为什么没被发现**: audit.sh 只检查文件是否存在/行数/骨架，不检查内容完整性；日记仍能被读取和索引，memory_search 还能命中，表面全绿
- **修复**: 逐文件解析冲突块，**两边内容取并集去重**（不是二选一，避免丢历史），备份 `/tmp/conflict_backup_20261101/memory_before_fix.tgz`，全局校验 0 残留、0 丢失行
- **教训**:
  1. **解决冲突不能只看当前冲突的文件**——`git status` 里 unmerged 的是提示，但 `git commit -a` 会把编辑器里所有残留标记一起收进去
  2. 提交前必须全仓扫描 `^<<<<<<< ` 标记，可写成 pre-commit hook
  3. audit.sh 缺「内容完整性」检查项，应在 L4 审计里加一条全局冲突标记扫描
  4. 无人读的日记＝坏日记。全绿报告掩盖了 4 天的数据损坏

## 2026-11-01 · ⚠️ `git stash pop` 会弹出历史遗留 stash —— 与 10/18 事故同源

- **现象**: 修身份文件时，为让 `git pull --rebase` 通过，对子模块改动做 `git stash push` → pull 后 `git stash pop` → **弹出的是 8 个月前的 `daily-audit-stash-2026-07-16`**，瞬间 29 个文件冲突（26 个 rename/delete + 3 个内容冲突），冲突里夹带 7 月日记、lessons、审计日志
- **根因**: `git stash push` 在无改动时不会新建 stash 条目，随后 `git stash pop` 就弹出栈里最老的遗留 stash。仓库里积压了 9 条历史 stash（最早 7/6），任何一次裸 pop 都可能炸
- **与 10/18 事故关系**: **完全同一机制**。10/18 日记已记录「Bug A：`git stash pop` 无条件执行 → 误弹历史遗留 stash」，当时只在 audit.sh 里修了，本次手工操作又踩一次
- **正确做法**:
  1. pop 前必须比对 `git stash list` 前后条数，确认 stash 是自己刚建的
  2. 或直接指定 `git stash pop stash@{N}`，不用裸 pop
  3. 或改用 `git stash create` 拿 commit hash（不污染栈）
- **本次处理**: 冲突现场先备份 `/tmp/stash_conflict_backup_20261101/` → 确认我的提交已推远端 → `git reset --hard HEAD` 恢复 → stash@{0} 保留未丢
- **教训**: **"清干净工作区"的快捷手段往往是事故源**。多 Agent 共享仓库尤其危险——别人的遗留 stash 里全是过期日记

## 2026-11-02 · 因果机制误判：位置相邻 ≠ 逻辑相关（严重）

**犯的错**：判断 `bypassDomain` 列表里含 `172.2*` → iPhone 热点 IP `172.20.10.x` 被 bypass → 路径 C 在热点下必然失败。

**实际是**：`bypassDomain` 是**客户端系统代理的排除列表**（决定 Mac 本机哪些流量不走代理），完全不参与决定「外部设备能否连上 Mac 的监听端口」。后者只由 `allow-lan`（bind 地址）+ 防火墙 + 路由决定。

**实测反证**：
```
allow-lan=false → bind 127.0.0.1 → 从 172.20.10.14 连入 ❌ 拒绝
allow-lan=true  → bind *        → 从 172.20.10.14 连入 ✅ 可连
```
测试机 IP 恰好就是 172.20.10.14（正在 bypass 范围内），但还是连通了 —— bypass 全程没参与。

**根因**：看到两个字段出现在同一个配置文件里，就假设它们有因果关系。位置相邻 ≠ 逻辑相关。

**关键自查法（以后必须做）**：**推极端验证**
> 如果我的因果链成立，推到极端会不会得出荒谬结论？
> 这次：bypass 也含 `192.168.*` → 按我的逻辑 C 在任何内网都永远不可行 → 显然荒谬 → 5 秒就能发现错。

**另一个自查**：**分清"配置项"属于哪一层**
- 应用层（客户端代理决策）
- 传输层（套接字 bind / 可达性）
- 网络层（路由 / 防火墙）
不确定就先问"这个字段生效在哪个环节"，而不是"它出现在哪里"。

**怎么被发现的**：Kitty 对等审查提出异议，并指出"192.168.* 也在 bypass 里，按你的逻辑推下去 C 永远不可行"——它用的正是推极端验证。**我该自己想到的。**

## 2026-11-02 · 「低频使用」≠「低价值需求」（认知偏差修正）

**我的错误推理**：
> workflow 面板近 3 个月只用 1 次（数据正确）→ 需求不成立，建议停止投入（结论错误）

**Daryl 的校准（原话）**：
> "在开发一个新的工作流的时候，可视化才能让我更快知道 Agent 到底操作逻辑是否正确，更快找到不符合需求的地方。就像你的『视频分析交互 workflow』，没有这个流程图，我很难理解你的代码层是怎么运作的、哪里需要调用哪个 LLM。不过确实没有迭代的时候我只需要『看』。"

**关键区分（我漏掉的）**：
| 使用频率 | 价值密度 | 类比 |
|---|---|---|
| 每天都在点 | 低 | 水龙头 |
| **一季度用几次，但每次用价值极高** | **高** | **灭火器** |

workflow 面板是**灭火器型工具**：平时不碰，但**新建/验收工作流时那一次，没有它就没法判断对错**。
我用"使用频率"去衡量它，等于用"水龙头标准"去评判"灭火器"。

**更重要的功能分层**（这是本质）：
- **验证性可视化**（读懂 Agent 逻辑对不对）← Daryl 真正需要的，价值最高
- **编辑性可视化**（拖拽改流程）← 我之前重点讨论的，其实次要
- **执行性可视化**（画完就能跑）← 我之前建议不要做的，现在看也确实不必

**我犯的错和上午 bypassDomain、ComfyUI 是同一个模式吗？**
不是。上午那两次是「混淆层次」（实现 vs 本质）。
**这次是「用错误的指标衡量价值」——用频率当价值的代理指标。**

**新自查规则（加入清单）**：
> 当我说"某功能没被使用所以不需要"时，先问：**这东西的设计使用场景是高频还是低频？**
> - 高频工具看频率
> - **低频但关键时刻必需的工具，看"缺了它会发生什么"，不看频率**
> - 具体检验：如果这东西消失，某类任务还能不能做？不能 → 它是必需的，频率低不等于不必要

**附带的正确判断（Daryl 也认可）**：他自己承认近 3 个月对 OPC 投入少——**所以"使用少"的另一个解释是"整个 OPC 都投入少"，不能归因到某一个模块**。这是归因错误，我把"大盘冷"读成了"这个模块不行"。

## 2026-11-03 · 「按最后一格取值」的时序陷阱（成本看板修复）
- **场景**：修每日成本图，方案文档要求取每个 agent `values` 的最后一格作为「当日用量」
- **坑**：agent 当日零消耗时，后端返回的 `labels` 数组**不会**为它补当天日期（因为根本没记录），尾部停在昨天。取「最后一格」= 把昨天的值当成今天
- **实测**：Self 11-03 零消耗，尾部是 11-02 的 $0.0625，四格合计 $0.4208 ≠ 台账 $0.3583 → 直接导致验收失败
- **通用规则**：**只要是对齐多序列的时间轴，永远按「目标日期」在下标里查，绝不能按「序列最后一格」取**。序列长度不齐是常态，不是异常
- **代码模式**：
  ```js
  // ❌ 错：序列不齐时会取到别的日期
  vals[vals.length - 1]
  // ✅ 对：先求全局最新日期，再逐序列 indexOf 对齐
  const idx = labs.indexOf(latestDay);
  const v = idx >= 0 ? vals[idx] : 0;
  ```
- **附带教训**：方案文档写的代码不能照抄。「文档作者已校验过行号」≠「文档逻辑正确」，行号对不对和方案对不对是两个独立问题。落地前要把方案代码在真实数据上跑一遍，用真实值算一遍合计

## 2026-11-03 · 写 fallback 时最容易把「错误行为」重新引入
- **场景**：修成本看板前端取值，主路径已改成「按 latestDay 对齐」，然后我"贴心地"给缺 label 的情况加了个 fallback：`vals[idx] ?? 取最后一格`
- **错在哪**：`取最后一格` 正是这次事故的病因本身。我把它当"兜底"又写回去了。缺 label 的含义是**当日无记录 = 0**，不是"用最近的旧值凑一个"
- **逮到方式**：构造「Self 缺 11-03 key」的反证场景跑一遍 → 合计 $0.5853 vs 期望 $0.5228，虚高 $0.0625
- **通用规则**：**写 fallback 前先问「主路径为什么要排除这种输入？」** 如果主路径排除它的理由正是"这样算会错"，那 fallback 不能悄悄把它算进去，只能返回"无数据"
- **更具体**：时间序列缺某天 ⇒ 0，不是前值填充。前值填充（ffill）在金融/成本口径里是**造假**，不是容错
- **同源教训**：这和 Balance 上一版「口头保证日期集合一致、实测不一致」是同一类——**都发生在"没有数据就不出声/用别的数顶上"的地方**。数据缺失必须显式表达（0 或 unavailable），不能靠推理补齐

## L-1107b｜「知道自己在猜」和「承认自己在猜」中间差一步（Atlas 钉出来的）

## 一、阻断级问题（必须先修，否则方案跑不通）

### 🔴 P0-1 路径 C（Mac 当旁路由）当前物理不可行

**方案写**：iPhone 手动配置代理指向 `Mac内网IP:7892`。
**实测**：
```
lsof -nP -iTCP:7892 -sTCP:LISTEN
→ wfnetwork 46319  TCP 127.0.0.1:7892 (LISTEN)   ← 只绑 loopback
```
配合方案自己记录的 App 配置 `allow-lan=false`，**手机根本连不上 7892**。

**修法**：路径 C 必须前置两步：① 微风设置里打开「允许局域网连接」；② 确认监听变成 `0.0.0.0:7892`。这两步方案里完全没写。→ 建议在方案里标注为「C 的前置条件」，否则下午会白试一轮。

### 🔴 P0-2 iOS 手工代理只覆盖 HTTP/HTTPS，不覆盖全部流量

iOS 的 WiFi「配置代理」只影响**遵循系统代理的 App**。不走系统代理的（自带网络栈、自行 DNS）会直连失败。
→ 这是路径 C 的**天花板**，不是 bug。方案里应写明"验收标准仅对浏览器/Safari/Chrome 有效"，不能承诺"手机全部 App 都能上外网"。若 Daryl 需要全 App 可用，只有 TUN 或手机装客户端能解决。

## 二、会导致"以为通过其实没过"的验收漏洞

### 🟠 P1-1 验收带宽单位不一致（会误判）

方案验收：`>30MB/s`（大写 B＝字节）
但方案自己记录实测：`4.57MB/s ≈ 36Mbps`

300M 宽带理论 37.5MB/s。当前 iPhone 热点 4.57MB/s。
→ `>30MB/s` 这个门槛**装完固宽后才勉强够**，而且如果实测是 Mbps 口径就会假通过。**必须统一成 MB/s 并写清"这是字节"**，或改成两档：合格 25MB/s / 优秀 35MB/s。

### 🟠 P1-2 「互联网共享 + TUN 冲突」仍无实测判据

Kitty 已诚实更正为"推断"，这点认可。但方案没给**下午怎么快速判定**。

```bash
netstat -rn -f inet | head -3     # 看 default 指向 utun* 还是 en0
```

## 四、我发现的、方案里没有的一个更大风险（单点故障）

### 🔴 P3-1 Gateway 的**全部** egress 都压在微风单个进程上

实测（本机当前状态）：
```
OPENCLAW_PROXY_ACTIVE=1
OPENCLAW_PROXY_LOOPBACK_MODE=gateway-only
http_proxy=https_proxy=http://127.0.0.1:7892
proxy.enabled=true
```

这说明 `proxy.enabled=true` 的实际效果**不是"只让 web_search 走代理"，而是 Gateway 全量 HTTP/WS egress 都走 7892**（官方文档 `docs/security/network-proxy.md` 已确认）。

**风险链**：微风进程挂 → DeepSeek API 调用全挂 → 四个 Agent 全部停摆 → 定时归档/成本扫描一起断。

**实测旁证**：走代理访问 LLM 反而更稳
| 路径 | 3 次延迟 |
|---|---|
| 直连 api.deepseek.com | 0.24s / **0.86s** / 0.20s（抖动） |
| 走 7892 | 0.19s / 0.18s / 0.19s（稳定） |

→ 走代理本身没问题，**问题是没有任何降级机制**。建议补一条：
- 监控 7892 端口存活（launchd KeepAlive 或 cron 探活）
- 探活失败 → 自动 `proxy.enabled=false` 回退直连 + 告警，而不是等全系统静默崩溃
- 这条建议的性价比**高于**网络方案本身，因为一次崩溃的成本（几个 Agent 停摆 + 重跑）远大于装宽带的折腾

另外实测：**本地服务走代理也正常**（`http://127.0.0.1:8765/api/costs` 走 7892 → 200 / 0.87s），所以不用担心中间件被代理搞挂。

# 第四轮审查（回应 P3-1 降级机制 · 12:10）

> Kitty 要求就「代理单点故障降级」给意见。我做了一组**故障注入实测**来定方案。

## 一、决定性实验：代理全挂时，国内服务还能不能活？

**构造**：`exclude-filter` 排除全部节点 → 代理组节点数 0（模拟机场整体挂掉）

**结果（无分流缺失，`GEOIP,CN,DIRECT` 生效）**：
| 目标 | 结果 |
|---|---|
| api.deepseek.com | **401 / 0.53s** ✅ 活 |
| open.feishu.cn | **404 / 0.45s** ✅ 活 |
| www.baidu.com | **200 / 0.24s** ✅ 活 |
| google.com | 000 / 10s ❌ 预期失败 |

**再构造**：订阅 URL 改成完全不可达的假域名 → **mihomo 依然正常启动**，`deepseek 401/0.70s`、`feishu 404/0.47s` 依旧存活。

### 结论（这条很关键）
**只要①代理进程活着 ②`GEOIP,CN,DIRECT` 类分流规则存在，则节点全挂 / 订阅不可达 / 机场跑路，国内服务（飞书通道 + DeepSeek API）全部照常工作。**

推论：**不需要「改 `proxy.enabled=false` + 重启 Gateway」这套重方案。** 那套动作代价是一次真实服务中断，且文档明确 `enabled=true` 但 URL 无效时受保护命令会 fail startup —— 反而把可恢复的降级变成硬故障。

## 二、给 P3-1 的三层降级设计

| 层 | 触发 | 动作 | 代价 |
|---|---|---|---|
| **L1 进程自愈** | 微风/mihomo 进程退出 | launchd `KeepAlive` 秒级拉起 | 秒级墙外中断，国内无感 |
| **L2 节点自愈** | 单个节点失效 | mihomo `health-check` 自动剔除（已在配置中） | 无 |
| **L3 机场整体挂** | 全部节点不可用 | **不动作**。接受墙外降级，保国内可用 + 告警 | 墙外不可用，但 Agent 存活 |

**L3 只告警不自动改配置** —— 因为实测证明 L1+L2 正确时，机场挂掉不影响 Agent 存活。自动改 `proxy.enabled` 反而是唯一会引入服务中断的操作。

## 三、纠正一个关键错误：探活对象选错了

Kitty 方案写「探 `7892` 端口」。**不够。**

- 端口活着 ≠ 代理可用：实测节点全空时，17895 端口仍在 LISTEN，但墙外全挂
- 应分两个探针：
  1. **国内探针（P0）**：直连 `open.feishu.cn` 或 `api.deepseek.com`，期望非 000 → 失败才是真故障
  2. **墙外探针（P1）**：走代理访问 `generate_204`，失败 = 降级，告警但不切

**分级逻辑**：国内挂 → 严重告警；仅墙外挂 → 降级提示。二者混淆会导致误判和误切。

## 四、「连续 N 次失败」参数建议

# 第五轮：撤回 P0-C（bypassDomain 判断错误 · 12:20）

> Kitty 对 P0-C 提出异议。我做了对照实验，**Kitty 正确，我的判断错误，此处正式撤回。**

## 一、我的原始错误结论（已撤回）

> ~~`bypassDomain` 含 `172.2*` → iPhone 热点 IP `172.20.10.x` 落在里面 → Mac 在热点下测 C 必然失败 → **必须先关热点接宽带（192.168.x.x）才行**~~

**三个错误，逐条认**：

### 错误 1：因果关系不成立（机制混淆）
`bypassDomain` 是**客户端系统代理的排除列表**，决定「Mac 本机哪些流量不走代理」。
它**不参与**决定的：外部设备能否连上 Mac 的监听端口。
后者只取决于 `allow-lan`（bind 地址）+ 防火墙 + 路由可达。

我把「客户端代理规则」当成了「服务端可达性规则」。

### 错误 2：自我否证（Kitty 指出的致命点）
bypass 列表里**同时含 `192.168.*`**。
所以"换成 192.168.x.x 就行"这个推论自相矛盾 —— 按我的逻辑，C 在任何内网地址下都永远不可行，这显然荒谬。
**一个推论如果推向极端会得出荒谬结论，说明推论本身错了。我当时没想到这一步。**

### 错误 3：实测直接反驳（最有力）
```
allow-lan=false → bind 127.0.0.1:17898 → 从 172.20.10.14 连入 ❌ 拒绝
allow-lan=true  → bind *:17897         → 从 172.20.10.14 连入 ✅ 可连
```
**我的测试机 IP 就是 `172.20.10.14`** —— 正好落在 `172.2*` bypass 范围内。
在 `allow-lan=true` 时，从这个"被 bypass 的地址"连入 **完全正常**。

bypass 列表全程没有参与。**Kitty 的结论 100% 正确。**

## 二、修正后的正确结论

| 判断 | 正确性 |
|---|---|
| 路径 C 失败的**唯一**原因是 `allow-lan=false` | ✅ 成立 |
| bypassDomain 会导致 C 失败 | ❌ **已撤回，因果关系不存在** |
| 「先关热点再测 C」这个**操作建议** | ✅ 仍然成立，但理由要改 |

**「先关热点」的正确理由**（两点，都与 bypass 无关）：
1. 避免 Mac 同时开热点 + 代理导致网络栈混乱
2. 移动端 IP 会变，配置写死 IP 会失效

## 三、Kitty 的排查方法（比我原来的好，采纳）

> 手机连 Mac 后 `telnet Mac_IP 7892`：
> - 连不上 + `lsof` 显示只绑 `127.0.0.1` → allow-lan 问题
> - 连不上 + `lsof` 显示 `0.0.0.0` → 防火墙或路由问题

**这是标准的分层排查法，我原来没有给出。** 已采纳为路径 C 的标准诊断流程。

## 四、Kitty 新增的 P0-C：`respect-rules` 不一致（我复核后认同）

| 来源 | respect-rules | proxy-server-nameserver |
|---|---|---|
| App `patchClashConfig` | **false** | `https://doh.pub/dns-query` |
| 订阅返回 | **true** | `43.108.56.44`（硬编码 IP） |

**这是真实的两套配置源，App 会覆盖订阅值。** 后果：
1. `respect-rules: false` → DNS 查询不遵循分流规则，被墙域名可能拿到污染 IP
2. `proxy-server-nameserver` 用 DoH 域名解析节点域名 → **循环依赖**，这正是上午 `dns resolve failed: couldn't find ip` 的根因

**这条我认同，且它解释了两个实测现象**（GEO 下载卡死、DNS 解析失败）。Kitty 这条发现质量很高。

**补充**：走路由器（mihomo 直接吃订阅）时用 `43.108.56.44` 是对的；走微风 App 时 App 用 doh.pub + `respect-rules: false`，是潜在泄漏点。两条路径行为不同，不能混用结论。

## 五、`respect-rules` 验收方法（替代原 dig 方案）

原验收 `dig +short open.feishu.cn` **本就不够**（已在前轮说明）。现在补上真正的判据：

| 要验证的 | 正确方法 |
|---|---|
| 分流是否生效 | 看 `respect-rules` 是否为 `true` |
| DNS 是否泄漏 | `curl -x <proxy> https://browserleaks.com/dns`，看解析服务器归属 |
| 被墙域名解析是否被污染 | 对比 `dig @127.0.0.1 -p 11056 <被墙域名>` 与真实 IP |

## 六、教训（已同步写入 lessons.md）

**这是本次协作我犯的第 2 个错，比第 1 个（样本量 3 当结论）更严重**，因为这次是**因果机制判断错误**，而不是表述不严谨。

`bypassDomain` 和 `ip:port` 确实是同一套网络配置里的两个字段，但它们作用于完全不同的层面（客户端代理决策 vs 服务端套接字可达性）。**位置相邻 ≠ 逻辑相关。**

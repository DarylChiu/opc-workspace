## 一、我们的失败复盘

### 1.1 GEPA 为什么在我们这失败了

GEPA 论文本身很强——ICLR 2026 Oral，平均比 GRPO 高 6%，用 35x 更少的 rollout。但它的成功条件和我们不匹配：

| GEPA 成功条件 | 我们的实际情况 |
|-------------|-------------|
| **明确的标量指标**（准确率、pass@k） | Agent 任务无单一指标，"完成得好"是主观判断 |
| **LLM-as-Judge 有标准答案** | 开放性任务没有标准答案可对比 |
| **任务边界清晰**（AIME数学题、代码优化） | Agent 任务跨域、多步骤、边界模糊 |
| **反馈闭环自动化** | 反馈依赖 Daryl 手动验收 |

**核心教训**：GEPA 不是自动进化系统的问题——是**我们没有给进化系统提供可度量的目标函数**。自动优化需要「什么是好」的清晰定义，Agent 任务恰好最缺这个。

### 1.2 SAGE Checker / Maker-Checker 为什么效果不明显

| 问题 | 根因 |
|------|------|
| 只审不修 | Checker 说「这里不对」，但没有修复机制，Agent 下次还犯同样错 |
| 反馈不积累 | 每次审查独立，A 任务犯的错不会在 B 任务中被预防 |
| 无闭环 | 审→改→交付 就结束了，没有「改了之后真的更好了吗」的验证 |
| 标准抽象 | "来源可追溯/结构化/逻辑严谨" 是好的方向，但对具体任务不够具体 |

**核心教训**：审查 ≠ 进化。审查是快照，进化需要**反馈→记忆→下次行为的因果链条**。

## 二、什么是真正有效的自进化

基于对 6 篇顶会论文 + 工业实践的调研，真正有效的 Agent 自进化系统有**三个共性**：

### 共性 1：可度量的目标函数

没有分数就没有进化方向。DSPy 的成功核心是「programming model + compiler + metric」。所有优化都围绕一个清晰的数值指标展开。

**对我们意味着**：需要为每个 Agent 的每个核心任务定义可量化指标。
- 搜索质量 → 基准测试分数（已有）
- 成本追踪 → 数据准确性（可量化）
- 代码质量 → 测试通过率/lint 分数
- 内容分析 → Daryl 评分（1-5）+ 修订次数

### 共性 2：记忆 + 检索 = 经验复用

Reflexion 的核心创新不是「让 LLM 反思」（谁都能做），而是**把反思存入 episodic memory，下次相似任务时检索复用**。

当前 Self 的 reflexion_journal.md 只有写入没有检索——经验被记录了但从未被消费。

**关键设计**：
```
任务到达 → memory_search 检索历史反思 → 
  如果找到相似失败模式 → 加载到上下文 → 执行时规避 →
  完成后反思 → 写入 memory →
  下次循环
```

### 共性 3：多轮迭代比一轮优化好

GEPA 维护 Pareto front（多个候选 prompt 并行演化），Reflexion 跑多轮 trial-and-error。核心逻辑：**一次修不好，但不放弃，多轮迭代逐步收敛**。

当前 Maker-Checker 只有 2 轮就放弃。实际需要的是「持续改进」而非「一次审过」。

## 三、可落地的方案方向（3个层级）

### L1 · 基础闭环（低风险，可立即开始）

**目标**：让 Agent 能从自己的错误中学习

| 改动 | 内容 | 参考 |
|------|------|------|
| **反思检索** | Agent 接到新任务时，先 `memory_search` 检索历史 reflexion_journal 中的相关失败记录 | Reflexion |
| **反馈消费** | Maker-Checker 审查意见写入 memory，下次同类任务自动加载 | Reflexion |
| **失败模式库** | 每个 Agent 维护一个结构化的 `memory/failure_patterns.json`，记录「什么场景→犯了什么错→怎么避免」 | Reflexion episodic memory |

**预期效果**：同类错误不重犯，SAGE/Checker 的审查结果真正被复用。开发量 ~2h。

### L2 · 指标驱动优化（中等风险）

**目标**：为可度量的任务建立自动优化循环

| 任务 | 指标 | 优化方式 | 参考 |
|------|------|---------|------|
| 搜索质量 | 基准测试分数 | 对比不同关键词策略的分数，自动选最优 | DSPy |
| 成本审计 | 数据准确率 | Balance 产出 vs 实际账单差异 | DSPy compiler |
| 代码生成 | 测试通过率 | 子代理生成→测试→反馈→重试（3轮） | Reflexion |
| 内容分析 | Daryl 评分 | 每次 Daryl 反馈作为训练信号 | RLHF 简化版 |

**关键约束**：只在有明确量化指标的领域做自动优化，不碰开放性任务。

### L3 · 多Agent博弈进化（高风险，暂不建议）

**目标**：通过 Agent 间对抗来提升质量

- Generator Agent + Critic Agent 持续博弈（类似 GAN）
- 但：需要大量 compute，效果不确定，GEPA 已经证明简单方案可能更好

**建议**：L3 暂时不做。先跑 L1 + L2 验证闭环可行性。

## 四、推荐方案：L1 完整闭环系统

基于当前基础设施（reflexion_journal.md + Maker-Checker + memory_search），搭建完整的「反思→记忆→检索→规避」闭环：

```
                    ┌──────────────────────┐
                    │   新任务到达          │
                    └──────────┬───────────┘
                               │
                    ┌──────────▼───────────┐
                    │ 1. 检索历史失败模式    │ ← memory_search reflexion_journal
                    │    加载到上下文        │
                    └──────────┬───────────┘
                               │
                    ┌──────────▼───────────┐
                    │ 2. 执行任务           │
                    │    （带着历史教训）     │
                    └──────────┬───────────┘
                               │
                    ┌──────────▼───────────┐
                    │ 3. Maker-Checker 审查 │
                    └──────────┬───────────┘
                               │
              ┌────────────────┼────────────────┐
              │                │                │
     ┌────────▼──────┐  ┌──────▼──────┐  ┌─────▼─────┐
     │ PASS → 交付   │  │ FAIL → 修改 │  │ 教训写入   │
     │ + 记录成功模式 │  │ (最多3轮)   │  │ memory     │
     └───────────────┘  └─────────────┘  └─────┬─────┘
                                               │
                                    ┌──────────▼───────────┐
                                    │ 4. 反思写入           │
                                    │    + 更新失败模式库    │
                                    │    + 下次检索可用      │
                                    └──────────────────────┘
```

### 具体改动项

| # | 改动 | 文件 | 工作量 |
|---|------|------|--------|
| 1 | 任务前检索：接到任务后 `memory_search` 查 `reflexion_journal` + `failure_patterns` | 4 Agent AGENTS.md | 30min |
| 2 | 失败模式结构化：`memory/failure_patterns.json` 替代自由文本 reflexion | 新文件 | 1h |
| 3 | Maker-Checker 审查结果写入失败模式库 | checker.py / reviewer.md | 30min |
| 4 | 3轮修改而非2轮（增加一轮深度修复） | AGENTS.md | 15min |
| 5 | 效果追踪：每周统计「有多少次检索到了历史教训并改变了行为」 | 周报模板 | 30min |

### 预期效果（对比 v1）

| 维度 | v1 (当前) | v2 (L1闭环) |
|------|----------|------------|
| 审查意见利用 | ❌ 审完即弃 | ✅ 存入记忆，下次检索 |
| 同类错误重复 | 频繁 | 明显减少 |
| 反馈到行为的延迟 | ∞（永不改变） | ~1个任务周期 |
| 进化可见性 | 无 | 周报有统计数据 |

## 五、决策需求 [P1]

1. **L1 闭环方案是否批准？** 不改架构，只在现有系统上加「检索→规避」闭环，低风险
2. **范围**：先只在 Self 试点（Self 已经有 Maker-Checker + reflexion_journal），还是 4 Agent 全上？
3. **失败模式库**：用结构化 JSON 还是继续自由文本？JSON 可查询但维护成本高，自由文本灵活但检索依赖 embedding 质量

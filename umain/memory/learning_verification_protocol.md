# learning_verification_protocol.md — 验收协议（2026-11-03 定型）

> 来源：2026-11-02/03 成本看板五层缺陷排查。三条规则全部从真实失误里长出来，不是通用规范。

## 核心三条

```
① 读之前：等文件稳定（时间戳连续 10 秒不变）
② 判断时：前提写成 assert 跑一遍，不口头保证
③ 落文档前：重跑一次，确认不是过期快照
```

| 规则 | 谁犯的 | 缺口 | 后果 |
|---|---|---|---|
| ① | Kitty（01:07 验中间态）| 验的是参数化过程中的随机切片 | 差点给假 PASS（数字 $0.5228 → 实际 $0.6609）|
| ② | Balance（口头保证日期集合一致）| 一致性这种性质没写成断言 | 差点交出坏契约（agent 日期不齐 → 图表错位）|
| ③ | Balance（01:11 读完就写文档）| 写完后没再确认一遍 | **真出错：把中间态当终态写进 patch 文档** |

**第③条最狠 —— 它是唯一真把错误写进交付物的。**

## 附加原则

### 断言有效性必须负向测试
**一个打不中的断言 = 没写。**

做法：造一个含 bug 的假版本，跑断言，必须 FAIL。
- 只有正向通过 = 只证明了「当前代码通过」
- 加上负向命中 = 才证明「断言能抓错」

实测案例（2026-11-03）：`verify_final.py` 的 [8] 前端防回退，注入原始 bug / 删 latestDay 两种假回归都能抓住。

### 断言判据用「错误模式」，不用「变量名匹配」
```python
grep "Object.values(daily)"  → 命中 1 次，但那是正确用法  ❌ 误报
grep "const days=daily?Object.values"  → 0 次  ✅ 按误用模式判
```
**否则正确用法触发假警报，然后有人会去「修」正确代码。**

### 浮动指标不设固定基准
`droppedDupes` 从 655 → 792 是正常的（随 session 重放次数增长）。
**只校验 `> 0`，不校验「等于某值」** —— 否则将来有人拿旧值当基准，花半天查一个不存在的回归。

### 正确性 = 跟数据语义一致，不是跟某行一样
实测：三种写法在同一场景（各 agent 日期不齐）下
```
原始 bug           → 合计 NaN（图坏）
「对齐已有正确行」  → 合计 1.0263  ❌ 误把昨天值当今日
「按语义显式定位」  → 合计 0.4671  ✅
```
**已有代码的正确性可能依赖前提**（657 行的正确性建立在"各 agent 日期集合相同"上）。前提一变就错。
→ **按语义写（"我要最新那天的值"），不按模式写（"别人怎么写"）。**

### 改频率 = 改可靠性等级（Balance 提出）
任务从「偶发」变「常态化」时，必须重审：
1. 写入原子性（并发截断风险）
2. 并发冲突（加锁 or 排队）
3. 失败可观测性（静默失败最危险）
4. 残留清理（tmp 文件）

> 一个每天跑一次的脚本可以有 bug 你都不知道；每 2 小时跑的东西，bug 会自己找上门。

## 跨 Agent 互审流程（本次实证有效）

**改动共享基建前，必须互审。** 今日实际收益：
- Kitty 单独查 → 只发现时区，改完数字还对不上，会回滚收场
- Balance 单独查 → 审出死代码和前端，但没人算 cron 成本，每月多花 $3.5
- 互审 → 五层缺陷全抓 + 省 $3.53/月 + 防了台账被并发截断

**分工建议**：一人审代码找契约断裂，一人端到端验算跑独立复现。不要两个人做同一件事。

## 五层缺陷模型（成本看板事故复盘）

| 层 | 缺陷 | 症状 |
|---|---|---|
| 数据层 | 时区 UTC + 无 responseId 去重 | 数字虚高 105% |
| 接线层 | 死代码，真值进不了图 | 图是错的但看起来"有数据" |
| 展示层 | 数组当数字 | 图永远错 |
| 契约层 | 日期集合不齐 | 图错位 |
| 验证层 | 口头承诺代替断言 | 差点把坑交出去 |

**核心洞察：五层互相掩护。任何一层单独修好，用户看到的都还是错的。**
→ 这解释了为什么 bug 藏了这么久：修一层看起来"没变化"，容易以为修错了地方然后回滚。
→ **排查这类"数字不对"的问题，必须从数据源到前端渲染整条链路验，不能只修看得见的那层。**

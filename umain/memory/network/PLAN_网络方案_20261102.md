### P2-2 修复方案（已实测跑通）

用 `proxy-providers` 吃原始订阅 URL + `exclude-filter` 自愈：

```yaml
proxy-providers:
  wf:
    type: http
    url: <订阅URL>
    interval: 86400
    header: {User-Agent: ["clash-verge/v2.0.0"]}
    health-check: {enable: true, url: "http://www.gstatic.com/generate_204", interval: 600}
    exclude-filter: "香港 02"
```

**实测**：provider 加载 55 节点（56−香港02），香港02 不残留，存活 49；
出口 `155.117.85.53`，Google `200 / 0.32s`。每日更新时坏节点自动剔除，自愈。

## 二·七、P0-D 分流规则修复（2026-11-02 12:05，第三轮 + 实测跑通）

### 最终方案：脚本生成完整配置（而非 proxy-providers）

`memory/network/build_mihomo_config.py`：
```
读 database.sqlite → curl 拉订阅 → 剔香港02 → 组名重映射
→ 修复DNS冷启动 → 生成内联配置(55节点+517规则) → API热重载
```

**为什么不用 proxy-providers**：实测 mihomo 内置拉取这个订阅会 `EOF`，
curl 同一 URL 同时刻返回 200。provider 自动更新在此订阅上不可靠。
另：订阅里没有独立 rules provider URL，rule-providers 方案不可行。

### 四个坑（都会在路由器上直接失败）

| 坑 | 现象 | 修法 |
|---|---|---|
| 坑1 订阅自举死锁 | `respect-rules: true` → 订阅域名被判进 PROXY → 代理未启动 → 拉不到订阅 | `respect-rules: false` + 规则首行 `DOMAIN-SUFFIX,weifengapi.com,DIRECT` |
| 坑2 节点域名只有私有DNS能解 | `asfhwsrgseg.weifengchat.vip` 在 223.5.5.5 / 119.29.29.29 / 114.114.114.114 / 8.8.8.8 **全部失败**，仅 `43.108.56.44` 返回 `ecs16-3.qishanmen.top.` | `proxy-server-nameserver` **只写** `["43.108.56.44"]`；加公共DNS会先返NXDOMAIN直接失败 |
| 坑3 mihomo拉取EOF | provider 拉订阅报 EOF，curl 正常 | 脚本 curl 拉取 + cron 刷新 |
| 坑4 DNS顺序冷启动超时 | 原订阅 nameserver 把 DoH/TLS 排前面，冷启动全超时 | 强制纯 IP DNS（223.5.5.5 等）置前 |

## 二·六、第二轮审查发现（2026-11-02 12:10，本机真实状态取证）

> 教训：**上一版方案读的是「plist 声明的配置」，不是「进程实际运行状态」**。
> 在微风这种 App 上两者差异巨大（patchClashConfig 会覆盖订阅值）。

### P0-B（最高优先级）微风不开机自启 = 24×7 断网隐患

实测：
```
系统启动 : Nov 1 16:02:57
wfnetwork: Nov 1 22:02:18   ← 晚 6 小时（手动启动的）
ps -p 46319 → ELAPSED 13:52:40，从没重启过，无守护
autoLaunch=false  silentLaunch=false  autoRun=false
~/Library/LaunchAgents/ 无 wf 条目，/Library/LaunchDaemons/ 也无
```

**后果链**：Mac 重启 → 微风不起 → `proxy.enabled=true` 但 7892 无人监听 → Gateway 全部 egress 失败 → 四个 Agent 同时停摆，且无自动恢复。

**修法（需 Daryl 授权）**：微风是 Flutter 应用，`autoLaunch` 走 SMAppService 不是 LaunchAgent。
正确组合应为三层：`autoLaunch=true` + `autoRun=true` + launchd KeepAlive。
（`autoRun=false` 时即使拉起 App 也不会自动连节点）

### P0-A 明文密码（需报 Daryl，不写入任何文档）

```
~/Library/Preferences/com.wfnetwork.plist  权限 600
flutter.password = 明文（不复述）
flutter.auth_token = JWT，无过期字段
```
权限 600 意味着其它本机用户读不到，但**任何有本机 shell 权限的 Agent 都能读**。
处置：报 Daryl 知情后决定，助手不改、不记录内容。

### P0-C App 运行时 DNS 与订阅不一致（真正的泄漏点）

```
App 运行时 patchClashConfig:
  respect-rules: false                              ← ⚠️ 不遵循分流，全走国内DNS
  proxy-server-nameserver: ["https://doh.pub/dns-query"]
订阅值:
  respect-rules: true
  proxy-server-nameserver: ["43.108.56.44"]        ← 硬编码IP，破解析循环依赖
```
两个独立配置源，**App 的 patchClashConfig 会覆盖订阅值**。
- 走路由器（mihomo 直吃订阅）→ 用 `43.108.56.44` 正确
- 走微风 App → 它用 doh.pub + `respect-rules:false`，是潜在泄漏点
- 上午踩的 `dns resolve failed: couldn't find ip` 根因即此：DoH 域名解析需要先解析，循环依赖

### 已复核确认的其他事实

| 项 | 实测值 |
|---|---|
| 防火墙 | `Firewall is disabled. (State = 0)` → 路径C无需额外放行 |
| TUN 设备 FlClash | 不存在 → TUN 从未启用，首次开启必然弹系统授权框，**需 Daryl 本人在场** |
| DNS 端口 | `0.0.0.0:1053`（非53），dig 需 `@127.0.0.1 -p 1053` |
| bypassDomain | 含 `172.2*` 和 `192.168.*`。⚠️但不影响手机连服务端，见下 |

**异议记录（已向 Bryson 提出）**：Bryson 认为 bypassDomain 含 `172.2*` 会拦住 iPhone热点 IP，
导致 C 必然失败。**实测反驳**：
1. `192.168.*` 也在 bypass 列表里，若此逻辑成立则 C 在任何内网 IP 下都不可行，自我否证
2. `bypassDomain` 是 Mac 本机系统代理的排除列表，只影响「Mac 上哪些流量不走代理」；
   手机从网络侧连 `Mac_IP:7892` 是否可达，取决于 `allow-lan` + 防火墙 + 路由，**bypass 列表不参与**
3. C 失败的唯一原因是 `allow-lan=false`
验证方法：`telnet Mac_IP 7892`。连不上且 lsof 只绑 127.0.0.1 → allow-lan 问题；
已绑 0.0.0.0 但连不上 → 防火墙/路由问题。

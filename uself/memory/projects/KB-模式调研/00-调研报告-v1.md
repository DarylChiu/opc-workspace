# 知识库搭建模式调研 v1：主流路线 vs 我们的 ACCA 知识树

- **作者**：Self（调研子代理）
- **日期**：2026-10-15（Asia/Saigon）
- **检索轮次**：15 轮 web_search（中英双语） + 3 次 web_fetch（1 次 404 失败）
- **验收标准（全文对齐的靶心）**：建好的知识库能让使用人（Daryl + 其他 Agent）**快速理解并引用**。分两条：① 人类 10 分钟内看懂一个陌生节点并顺链找到上下文；② Agent 能以低成本拿到精确定位的内容 + 出处。
- **评价原则**：不追求行业标准；凡对上述两条无增益的先进技术，一律判"不做"。

---

## 1. 一句话结论

**跟进，但只跟进一条：把现有的 Markdown 五域树升级为「编译式知识库 + 显式寻址契约」（Karpathy LLM-Wiki / Google OKF 路线）——即补上 `index.md` 导航层、稳定的节点 `id` 与「摘要/适用范围/最后复核/出处」四行契约、以及一个只读的取数接口（AGENTS.md 声明 → 有条件上 MCP）。**

**不跟进**：GraphRAG 建图、独立向量库/RAG 服务、托管式 Agent 记忆服务（Mem0/Zep 类）。

**决定性事实**：Google 2026-06 发布的 Open Knowledge Format 规范，把知识定义为「markdown 目录 + YAML frontmatter + index.md/log.md」，**与我们现有形态（Obsidian Vault + frontmatter + wikilink + 五域树）几乎同构**——我们缺的不是技术栈，是「让 Agent 能低成本取到并署名引用」的那一层契约。4 个月 0 次 `query_node` 说明当前失败点不在检索算法，在**取数成本**：Agent 要内容必须人肉求 Self，这个链路对使用人是负收益的。

## 2. 主流模式图谱（8 类）

| # | 模式 | 代表做法 / 工具 | 它主张什么 | 代价是什么 |
|---|------|----------------|-----------|-----------|
| 1 | **经典向量 RAG** | LangChain / LlamaIndex + pgvector / 各类向量库 | chunk + embedding 语义召回，把"相关片段"塞进 prompt | 切块破坏上下文；相似度 ≠ 语义；需要维护摄取管道；**Agent 拿到的是 top-k 片段而非可署名的完整节点**——对"引用"是降级 |
| 2 | **GraphRAG / 知识图谱增强检索** | Microsoft GraphRAG、Neo4j | 显式实体-关系 + 社区摘要，解决多跳与"全局性问题"，可解释性来自证据路径 | 索引成本极高：10K tokens 文档要 5–15x token 的 LLM 调用（实体抽取+摘要），小时级建图；更新要重建社区；GraphRAG-Bench 实测 **global search ≈ 331K prompt tokens/问**；产物是机器图，不是人读的页面 |
| 3 | **LightRAG / 轻量图索引** | HKU LightRAG、LazyGraphRAG、HippoRAG2 | 保留图索引、去掉社区遍历，检索用向量取实体/关系，图只做结构补全，成本远低于 GraphRAG | "便宜"只是相对 GraphRAG：同一基准下 **LightRAG ≈ 100,832 tokens/问 vs 向量 RAG ≈ 879**，仍高两个数量级；依然需要图构建与一致性问题 |
| 4 | **长上下文替代检索**（context stuffing） | Gemini / Claude / GPT 长窗口 + 全量灌入 | 窗口都 1M 了，直接把语料塞进去，理论上是"不用检索" | Chroma「Context Rot」研究：18 个前沿模型在**远低于标称上限**时准确率已开始下降；成本约 30x/查询；中段事实仍会漏。2026 生产共识 = **路由器**（按查询分派 RAG 或长上下文），不是替代 |
| 5 | **Agentic memory 层** | Mem0（ECAI 2025, arXiv 2504.19413）、Zep/Graphiti（时序知识图, arXiv 2501.13956）、Letta/MemGPT | 把 **记忆（episodic/个性化，per-user）** 与 **知识（静态/共享）** 分层；Zep 把"某人在 2 月前拥有预算"做成时序一等查询；Mem0 自动抽取事实并去重 | 面向对话连续性与个性化，不是面向"可署名知识"：产出是事实条目，**没有人类可读页、没有出处链**；且基准数字厂商口径互相矛盾 |
| 6 | **结构化优先 / semantic layer / MCP 化知识服务** | Cube、AtScale、Atlan；Gartner 预测 2027 前 | Agent 不写 SQL，通过 MCP **按名字取"指标/维度/表"**；治理在语义层，Agent 层与口径解耦 | 前置投入大（先要有治理好的语义层）；管的只是**指标与数据资产**，对"概念/判断/经验/踩坑"这类知识无效 |
| 7 | **Agent-native 文档协议** | `llms.txt`（llmstxt.org v2，2025-07 时 600+ 站点采用）、`AGENTS.md`（OpenAI 2025-08 发布，2025-12 由 Linux Foundation 的 Agentic AI Foundation 托管）、`CLAUDE.md` | 给仓库/站点放一份"写给 Agent 读的说明书 + 目录"，让 Agent 有确定的入口和约定 | 只解决**入口与约定**，不解决**内容本身可寻址**；llms.txt 存在争议（被质疑是 AI 时代 SEO 新瓶 / 也可能纯属无效仪式） |
| 8 | **人类可读 wiki + LLM（编译式知识库）★** | **Karpathy「LLM Wiki」gist（2026-04，5000+ stars）**、**Google OKF v0.1（2026-06-12）/ v0.2（2026-07-24）**、Obsidian + CLI agent | 三层：`raw/`（不可变一手源）+ `wiki/`（LLM 维护的编译产物 md）+ `schema`（CLAUDE.md/AGENTS.md 约定）；三操作：ingest / query / lint；`index.md` 做内容目录（渐进式披露）+ `log.md` 做 append-only 时序日志（可 grep）。**"知识编译一次并保持最新，而不是每次查询重新推导"** | 需要主动维护（lint 查陈旧声明、矛盾、孤页、断链）；人必须承担"选源 + 提问 + 判断"，否则 wiki 同样腐化；无 lint 的 wiki 腐化速度可能快于向量库 |

**规模门槛（关键量化）**：多源工程共识是**语料 < ~50 文档先别上检索层**，直接索引+按需读取；Anthropic 官方把 "just-in-time context retrieval" 的主键定为**文件系统**而非向量库（Claude Code 模式 = 一个索引文件 + 按需加载的 md）；Karpathy 明确 `index.md` 在 **~100 源 / 数百页**规模"工作得出奇地好，且不需要 embedding RAG 基础设施"。

> 我们的位置：**219 个 .md**——正好落在这个"结构化索引完全够用"的区间上沿，尚未越过必须上检索层的线。

## 3. 近几个月（2025 H2 至今）的新技术路线

> 强调"相对上一代变了什么"，按时间倒序。

1. **编译式知识库从"模式"变成"标准"**（2026-04 → 2026-07）
   - Karpathy gist（2026-04）提出三层 + 三操作 → Google Cloud **OKF v0.1（2026-06-12）、v0.2（2026-07-24）**把 `markdown 目录 + YAML frontmatter` 规范化为 vendor-neutral 标准，**唯一必填字段 `type`**，可选 `title/description/resource/tags/timestamp`，保留文件名 `index.md`（渐进式披露导航）与 `log.md`（变更史）；Google 已让 Knowledge Catalog 摄取 OKF bundle。
   - **变在哪**：上一代把知识当"待检索的语料"（检索成本在每次查询）；这一代把知识当"待编译的产物"（成本前移到每次摄取一次，之后永远便宜）。这正是我们已经在做但没做完的事。

2. **渐进式披露（progressive disclosure）成为 Agent 上下文工程主范式**（2026）
   - 机制：一级只放"短描述/目录"常驻上下文，命中才加载正文（Anthropic skills 的 `SKILL.md` 模式、OKF 的 `index.md`、diataxis 式的分层文档）；学术侧有 arXiv 2607.17598《Is Progressive Disclosure All You Need for Long-Context Agents?》（2026-07）。
   - **变在哪**：从"检索得更多"转向"先导航、后加载"。**这是唯一同时服务你两条标准的机制**——因为人类的阅读路径（看目录→点进去→顺着链接走）和 Agent 的加载路径第一次变成同一条。

3. **长上下文没有杀死检索，而是把架构推向"路由器"**（2026）
   - 多源一致：RAG 未被取代；Chroma context rot 给出量化反面证据；生产架构 = 按查询分派（小范围→塞全量，大范围→检索+重排）。附带证明：**"上下文窗口大小 ≠ 检索质量"**，这是 2026 最贵的架构错误之一。

4. **图检索进入"性价比审计"阶段**（2026）
   - LightRAG / LazyGraphRAG / HippoRAG2 都在削社区遍历；GraphRAG-Bench 把 token 账公开化：**向量 RAG 879 / HippoRAG2 1,008 / GraphRAG local 38,707 / LightRAG 100,832 / GraphRAG global 331,375（prompt tokens per question）**。
   - **变在哪**：问题从"要不要上图"变成"这张图值不值这个 token 账单"。

5. **Agent 记忆与组织知识正式分层**（2025-01 起，2025–2026 成熟）
   - Zep/Graphiti（arXiv 2501.13956）时序知识图；Mem0（ECAI 2025, arXiv 2504.19413）在 LoCoMo 上做十种记忆方案横评（含 RAG、full-context、OpenAI Memory）。
   - **变在哪**：把"对话历史/个性化记忆"和"组织知识"分仓。混在一层是上一代的错误——也解释了为什么拿记忆型工具来做"知识库"会出问题。

6. **"让别的 Agent 来查"从私有协议升级为标准协议**（2026）
   - AWS Bedrock KB 经 AgentCore Gateway 暴露为 MCP 工具；Azure AI Foundry IQ 知识库有 MCP endpoint；多 Agent 共享上下文的三种接口模式：MCP resource / 直连图查询（Cypher/SPARQL）/ REST-GraphQL。
   - **变在哪**：我们早期设计的 `query_node: 编号` 协议**方向是对的，形态过时**——同一个思路现在有标准载体，不需要自造协议，也不需要向量库（MCP server 直接读 md 就够）。

## 5. 是否需要跟进（三档）

### ① 现在就做（三条，全部直接指向"快速理解 + 引用"）

**A. 补编译产物的两个保留文件：`index.md` + `log.md`**
- 内容：`index.md` = 全树目录，每节点一行「路径 + 一句话摘要 + 状态（现行/待复核/已废弃）」；`log.md` = append-only 摄取日志（固定前缀便于 `grep '^## \[' log.md | tail -5`）。
- 为什么对验收标准有增益：人类入口从"打开目录树猜"变成"读一页索引"；Agent 一次文件读取即可定位，替代人肉转述。

**B. 建立节点契约：稳定 `id` + 顶部四行块**
- 每篇 frontmatter 增 `id`（短、稳定、永不变，改名不影响引用）；正文顶部固定四行：**一句话摘要 / 适用范围（什么时候该看它）/ 最后复核日期 / 出处**。
- 为什么：这是"引用"从"能引用"变成"敢署名引用"的最小改动——引用形态变成「节点 id + 段落标题 + 最后复核日期」。

**C. 内容重心倒转：从"先长齐树再嫁接"改为"事件驱动嫁接"**
- 停止从公开资料往下铺叶子；改为**每次 Daryl 做判断/定口径/踩坑/返工发生时，就地生成 1 个节点并挂到已有树枝**。
- 为什么：先验已被自己的数据证伪（183→219 的增长没有带来任何调用）；公开资料部分价值最低——它天然不可引用（出处是外部原文，不是我们的口径）。

### ② 看条件（触发式，别提前上）

- **本地混合检索（BM25 + 向量，如 on-device 搜索 + LLM 重排那类方案，含 MCP 形态）**：触发条件 = 树 > 500–800 节点，或 `index.md` 单文件 > 8–10K tokens 导致难以一次读完。在此之前 `index.md` 足够。
- **MCP 取数服务**（若短期只想做 C 项的一半）：先用 `AGENTS.md` 写清"何时查、怎么查、怎么引"，验证是否有 Agent 真的来查；有需求再做 stdio server。
- **向量库 / RAG 服务**：触发条件 = 输入源变成大量非结构化外部语料（PDF/合同/会议录音）且查询需要跨语料召回时。

### ③ 不做（理由必须落在"对『快速理解并引用』无增益"）

| 不做的东西 | 为什么它对「快速理解 + 引用」无增益 |
|-----------|--------------------------------|
| **GraphRAG 全量建图** | 它的核心增益是跨文档多跳与全局摘要——我们的问题不是"总结不出来"，是"没人来拿 / 拿不到"。且它把知识变成机器图（**人类不可读**），token 账单高出向量 RAG 1–3 个数量级（global search ≈331K tokens/问），产出物也不是 Daryl 能直接引用的句子。**对两条标准：0 增益，甚至反向。** |
| **独立向量库 / RAG 服务** | 在 219 文件规模上，它把"可署名的完整节点"降解成"top-k 片段"，**引用精度反而下降**；工程共识（<50 文档先别上检索层、Anthropic 用文件系统做 just-in-time 检索）与本案例规模都指向同一个答案。**对②是负增益。** |
| **托管 Agent 记忆服务（Mem0 / Zep / Letta）** | 它们解决的是**对话记忆与个性化**，产出是事实条目，**没有人类可读页、没有出处链**——引用时给不出"哪一页/谁定的/什么时候"。**对①无增益，对②是负增益。** |
| **LLM 自动生成整棵树（无人参与）** | 你在 10-07 已关闭 SAGE Checker 与 Maker-Checker，方向是减负；而无人参与的 wiki 会漂移（陈旧声明、矛盾、孤页）——维护好是复利，维护差是负债。**收益不确定，风险确定。** |

## 6. 可直接落地的 3 个最小动作

| # | 动作 | 预计工时 | 对「理解 + 引用」的增益 | 成本 |
|---|------|---------|---------------------|------|
| 1 | **生成 `index.md` + `log.md`**（脚本遍历 219 个 md 抽 frontmatter 的 title/type/parent，按五域分组输出；摘要缺失的节点标 `⚠️ 待补摘要`，log.md 从首次提交开始写） | 0.5 天 | ① 人类首次理解一个陌生域的时间从"翻目录树"降到"读一页索引"；② Agent 单次文件读取即可定位节点，不再需要人肉转述 | $0（本地脚本，无 API 调用） |
| 2 | **节点契约补丁**：frontmatter 加 `id`（稳定短码）+ 顶部四行块（摘要 / 适用范围 / 最后复核 / 出处）；**先做 top 50 高频节点**，并写一个 frontmatter 校验脚本挂到 23:59 cron（查缺字段/过期复核/断链/孤页） | 1–1.5 天（含脚本） | ② 引用可直接给出「节点 id + 段落标题 + 最后复核日期」→ 从"能引用"升级为"敢署名引用"；① 摘要行让 10 分钟看懂成为结构性保证 | $0（本地）；cron 校验默认不调 LLM |
| 3 | **取数接口**：`AGENTS.md` 里加一节「ACCA 知识树：何时查 / 怎么查 / 怎么引」+ 一个只读工具（本地 stdio，暴露 `list / search / get` 三个动作，直接读 md，无向量库）；若 Agent 侧暂不支持 MCP，先落一个约定好的 CLI 命令 | 1 天 | ② 其他 Agent 的获取成本从"求 Self（≈小时级、依赖人在）"降到"一次工具调用（≈秒级）"；**这是唯一可测量的修复**：指标 = `query` 次数从 0 → ≥N/月 | $0–少量（本地运行；若走 MCP 需 Agent 侧配置） |

> 三项合计约 2–3 天，全部 $0 API 成本。**先做 1 再做 3 再做 2**（1 提供寻址基础，3 立刻验证需求真伪，2 是精修）。

## 8. 不确定性与反面证据

### 8.1 属于推测的结论

- **"不上 GraphRAG/向量库对我们无增益"**：方向有强证据（我们的问题类型、规模门槛、Anthropic 的文件系统优先、Karpathy 的 ~100 源经验值），但**没有针对"200–400 节点中文+英文混合、含决策类知识"的直接 A/B 数据**。这是推断，不是实验结论。
- **"补 index + id 后 Agent 会来查"**：这是我把"4 个月 0 调用"归因为**取数成本**而非**需求不存在**的推断。**反面可能**：其他 Agent 根本没有需要 ACCA 知识的任务（此时做了接口仍是 0 调用，但成本只有 ~2.5 天，可承受）。建议动作 3 先做最小验证，别先做全套 MCP。
- **"事件驱动嫁接优于先长齐树"**：基于我们自己 183→219 的失败数据 + 多个来源的"公开资料低价值"论断，但样本只有一个。

### 8.2 厂商营销口径（已在结论中降权）

- Mem0 / Zep 的基准数字互相矛盾：mem0.ai 自家博客称 LongMemEval 上 **Mem0 93.4 vs Zep 71.2**，而 Zep 侧论文指出 Mem0 graph 构建/一致性问题。**双方都是卖方**，数字不可作为选型依据。
- Atlas / Cube / AtScale（语义层厂商）与 TigerGraph / Meilisearch（图/检索厂商）的对比文章都带有"引流到自家方案"的动机；Gartner 预测（"降低 60% 成本"）是**转引自厂商博客**，未找到一手报告，置信度低。
- "LightRAG 比 GraphRAG 便宜 6000x" 这类说法来自 LightRAG 阵营口径，与 GraphRAG-Bench 的绝对数字（LightRAG 仍是向量 RAG 的 ~100 倍）冲突。**采信后者**（基准数据集测量 vs 阵营宣传）。

### 8.3 我没有找到证据的部分（直说）

1. **Google Cloud 官方博文一手源抓取失败**：`https://cloud.google.com/blog/products/data-analytics/introducing-the-open-knowledge-format` 返回 **404**（2026-10-15 实测）。OKF 结论基于 6 篇二级来源的一致描述 + explainx 引用的 spec 路径（`GoogleCloudPlatform/knowledge-catalog → okf/SPEC.md`）。**版本细节可能不准**：有来源称 v0.1（2026-06-12）、v0.2（2026-07-24），也有来源只写 v0.1。
2. **未找到**编译式知识库在"200–400 节点"这一具体规模的量化效果对比（检索延迟、引用准确率、人类理解时间）——所有"index.md 够用"的说法都是定性经验。
3. **未找到**中文侧对 LLM Wiki / OKF 的落地讨论（15 轮检索中中文结果清一色是"向量 RAG + GraphRAG + 权限"那一套）。可能是中文社区滞后半年，**也可能是我的中文查询词覆盖不足**——两种解释我无法区分。
4. **未找到**"AI 维护的知识节点在合规/审计场景的可引用性"标准。对 ACCA/财务场景这是关键空白（审计要求可追溯、可复核、有责任人，而 OKF 的 `timestamp` 只是建议字段）。**这块需要 Daryl 定口径，不是我能检索出答案的。**
5. **未独立复核**任务给定的实测数据（219 个 .md、4 个月 0 次 `query_node`、142/46/15/7/0 的分布）——我按任务描述采信，未访问 vault 验证。
6. **AGENTS.md 的治理时间线**（OpenAI 2025-08 发布 → 2025-12 Linux Foundation 托管）仅有单一来源（Data Panda），未交叉验证。
7. **"llms.txt 是无效仪式"** 的怀疑方（Peec AI 等）与支持方（llmstxt.org 、Mastercard 等采纳方）都存在，**我给不出裁决**——但这一点对本决策无关紧要（我们的取数对象是内部 Agent，不是公网爬虫）。

### 8.4 反方最强论点（必须记录）

> **DataCamp**：RAG 建库后接近零维护（索引是机械动作），而 LLM Wiki **需要主动维护**——lint 查陈旧声明、查矛盾、清孤页。**如果不做 lint，编译式知识库的腐化速度快于向量库。**

对这个反论我的判断：在**有 agent 可代跑 lint** 的前提下，维护成本近零（Karpathy：LLM 不会累、不会忘记改交叉引用、一次能改 15 个文件）；但前提是**lint 必须真的挂在 cron 上**——我们已有的 23:59 compliance cron 正好是免费载体。若不做 lint，反方论点成立，此时更保守的选择是**只做 `index.md`，连节点契约都别铺**。

> **第二反方论点**：如果 Daryl 的真实用途只是"十年后自己翻得到"，那么连 MCP 都是过度设计——`index.md` + 现有双链已经满足全部需求。"Agent 可引用"这条标准的真正用户是**其他 Agent**，而这件事的成立与否目前**没有被验证过**（0 次调用）。所以动作 3 应该是**先验证需求真伪**，而不是先建服务。
